**自動で走らせてよい仕事は少ない。**多くを仕掛けると、通知が読まれなくなって
全部が無駄になる。ここは「何を仕掛けるか」を決めるところで、
登録の作法は skill `schedule` に任せる。

## 1. いまの状態

`.claude/policy.yml` の `routines` に、仕掛けてあるものと**その狙い**が書いてある。
**実際に登録されているかは別**なので、skill `schedule` の一覧で確かめる
(ずれていたらどちらかを直す)。

`$ARGUMENTS` が `--list` ならここで終わる。

## 2. 仕掛けてよいものか

3 つ全部に当てはまるときだけ仕掛ける。

| 条件 | 外れる例 |
|---|---|
| **人が忘れる** | 毎回やっているものは自動にしなくていい |
| **結果を読む相手がいる** | 誰も読まない報告は、動いていないのと同じ |
| **走った結果で何かが変わる** | 「見るだけ」の定期実行は、通知を鈍らせるだけ |

### このプロジェクトの周期

- **月次の再学習**(`docs/operations.md` の「月次再学習」)。**人が忘れる周期。**
  ただし学習そのものを自動で回すのではなく、**「そろそろ回すころだ」と
  言うだけ**にする。学習は窓とフラグを間違えると黙って壊れる
- **取り込みの穴。**`ingest` は日単位で、抜けた日は静かに残る。
  「直近 30 日で未取得の日」を出すのは、走った結果で行動が変わる
- **`/standup --since <前のタグ>`** を、区切りのときに。**定期ではなく手で**

**効かないもの:** 毎日の診断(読まれなくなる)、コミットのたびの通知
(フックの仕事)、スクレイピングの定期実行(**規約上グレーで、
レート制御と停止スイッチが人の目の下にある前提で回している**)。

## 3. セッションの中で繰り返すだけなら

定期実行ではなく、**いま開いているセッションの中で**繰り返したいだけなら
`/loop` のほうが安い(登録も要らず、止めるのも簡単)。
学習の進み具合を見るのはこちら。

「来月」「毎週」のように**セッションを越える**ものだけを routine にする。

## 4. 仕掛ける

skill `schedule` を呼んで登録する。**登録の前に、次を見せて承認を取る:**

- 何を走らせるか(コマンド)
- いつ(cron)
- **何が出てきて、それを誰がどう読むか**
- 止めかた

**スクレイピングを伴うものは仕掛ける前に必ず聞く。**

## 5. 体制に書き戻す

登録したら `.claude/policy.yml` の `routines` に書く。**書かないと、
半年後に「誰が仕掛けたか分からない定期実行」になる。**

```yaml
routines:
  - name: monthly-retrain-reminder
    when: "0 9 1 * *"
    does: /standup docs-auditor
    why: 月次再学習の周期。回したのに docs の数字が動いていない状態を捕まえる
```

## 6. 効かなくなったら外す

**読まなくなった定期実行は、その場で外す。**「あとで読む」で残すと、
他の通知まで読まれなくなる。外したら `routines` からも消す。
