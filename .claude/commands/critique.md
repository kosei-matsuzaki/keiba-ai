**機能が要るか、順番は合っているか、その結論を信じてよいかを疑う。**
コードが正しいかは見ない。

## 1. 立場を切り離す

**このコマンドの本体は agent に投げる部分。**同じ会話で実験を回した Claude は、
出た結果に肩入れする。`.claude/agents/critic.md` へ、
**会話の経緯を渡さずに**投げる。

| 引数 | 誰が読むか |
|---|---|
| なし | `critic` |
| `--as <役名>` | その立場だけ |
| 論点 / パス | その範囲だけを見せる |

このプロジェクトに `user-voice` は置いていない(動かすのは自分だけ)。
`marketer` も置いていない(収益を求めていない)。

## 2. 何を渡さないか

渡すのは範囲だけ。**渡してはいけないもの:**

- なぜその損失・その買い方にしたか(会話でしか存在しない理由)
- **どの実験が「効いた」と思っているか**
- どれだけ時間をかけたか

これらは「直さないほうがよい理由」として効いてしまう。判断材料ではない。

## 3. 台帳を先に読む

```bash
cat .claude/judgments.yml
```

**前に「いまは直さない」と決めたことを蒸し返さない。**覆すなら、
「何が変わったから覆すのか」を言う。言えないなら黙る。

## 4. このプロジェクトで特に疑うところ

- **窓の長さ。**「効いた」の根拠が単一 holdout なら、前進検証で消える形と
  同じかどうかを見る。実際に消えた例が `docs/archive/2026.md` に複数ある
- **一度外して戻したもの。**EV・Kelly・戦略プリセット・外部の確率校正は
  全廃済み。**戻す提案には、廃止したときと違う証拠が要る**
- **選ばせているものの数。**設定項目・損失の種類・実験ノブは、
  増えるほど「どれで測ったか」が分からなくなる
- **運用モデルが 2 本あること。**active と確率モデルを分けている代償を、
  払うだけの差が測れているか

## 5. 出す

**多くても 5 件。**効き方の大きい順。各件はこの形:

```
所見: <一文>
根拠: <path:line か コミット。無ければ「印象」と明記>
効き方: <直すと何が変わるか>
代わりに: <別の解き方。無いなら「無い」と書く>
確からしさ: 確か (読んだ) / 推測 (測っていない)
```

最後に **1 行だけ**、いちばん効くものを名指しする。

意見が割れたら、**割れたまま出す。**そこが本当の論点。

## 6. 決まったら残す

「いまは直さない」と決めたものは `.claude/judgments.yml` へ
(書式は `/standup` の 4 節)。

## やらないこと

- 褒めない。良い点は最後に 1 行だけ
- コードを書かない。**このコマンドは何も直さない**
- 「一般にこうすべき」で言わない。**このリポジトリの証拠で言う**
- **否定済みの仮説を提案しない。**`docs/archive/2026.md` を先に読む
