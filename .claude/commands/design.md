**見た目を好みで決めない。**この画面が**何を判断させるものか**から決める。

skill `frontend-design` があれば**先に読む**。配色・字・構造の決め方の一般論は
そこにある。**このコマンドが持つのは、このプロジェクト固有の部分だけ。**

## 0. 規定の置き場所について

規定は `docs/design.md` の「フロントエンド スタイル設計」と「UI スタイル方針」。
**ただしこの文書は、アーキテクチャ図・AI モジュール設計・状態管理も持っている。**
規定を足すほど 1 つの文書に 2 つの話が濃くなる。

**分けるのは `/docs` の仕事。**ここでは分けない。ただし
「また 1 つ足した」と報告に書く。

## 1. 対象を決める

| 引数 | 何をするか |
|---|---|
| なし | 規定 `docs/design.md` を作る / 直す。画面は触らない |
| 画面名 | その画面を規定に沿って作る・直す |
| `--renew` | **刷新。**方向から決め直して、全画面に当てる |
| `--read-only` | 測って報告するだけ。書き換えない |

`frontend/src/` が対象。画面は `frontend/src/routes/`、部品は
`frontend/src/components/`。**規定が無いのに画面から直さない** — 直した先が
散らばるだけで、次に足す画面もまた散る。

## 2. いまを測る

**数える。**「なんとなく古い」ではなく、種類の数で言う。

```bash
grep -rnoE '#[0-9a-fA-F]{3,8}' frontend/src \
  | sed 's/.*://' | sort | uniq -c | sort -rn | head -20
```

**このリポジトリでは、色がベタ書きされていること自体が逸脱。**
CLAUDE.md に「ハードコードの Tailwind カラークラスではなくバリアントを使う」と
書いてある。出どころは `frontend/src/globals.css` の CSS 変数と
`frontend/tailwind.config.ts`。

```bash
# 定義されているトークン
grep -nE '^\s*--' frontend/src/globals.css | head -40
# 画面にベタ書きされた Tailwind の色
grep -rnoE '\b(bg|text|border)-(red|blue|green|yellow|gray|slate|zinc)-[0-9]{2,3}' frontend/src | wc -l
```

余白・角丸・字の大きさも同じように集める。見るのは:

| 見るもの | 何が分かるか |
|---|---|
| 値の種類の数 | 多いほど散っている。**刷新の理由はここに出る** |
| 尺度に乗っているか | 余白が 4 の倍数か。中間値が生えていないか |
| 出どころ | `globals.css` 1 か所か、画面にベタ書きか |
| 状態の抜け | 空・読み込み中・エラー・長文の分岐があるか |
| 規定との差 | `docs/design.md` に無い値がいくつあるか |

**このプロジェクトは「空」が普通の状態。**スクレイピング済みデータも学習済み
モデルもリポジトリに含まれないので、**初回起動は全画面が空**。
空の見え方を測らないのは、いちばん多い状態を見ていないということ。

## 3. 方向を決める

**ここが本体。**規約 `.claude/policy.yml` から読む:

- `project.what` — 何を解くものか
- `project.users` — **自分だけ。**他人向けの説明的な UI は要らない代わりに、
  **判断が速いこと**がすべて

次の 2 つは**推測で決めない。読み取れなければ聞く:**

| 決めること | なぜ聞くか |
|---|---|
| 使う状況 (レース直前か、あとで検証するときか) | 密度と、何を先頭に出すかが変わる |
| 避けたい印象 | 「既視感がある」は、避けたいものが決まって初めて避けられる |

**2〜3 案を、言葉で先に出して選ばせる。いきなり実装しない。**各案に:

```
案 A: 「発走前の 5 分」
  方向  1 画面 1 判断。買うか買わないかだけが目に入る
  配色  地は落ち着いた暗色。差し色は「買う」の 1 つだけ
  密度  一覧の情報量を捨てる。確信度と点数以外は畳む
  捨てる 検証のための数字。それは Ledger 側の仕事にする
```

**「既定に見えるもの」を避ける** — どのダッシュボードでも見た配色、
意味の無いグラデーション、数字を大きくしただけの KPI カード。
捨てたものを案に書く。

## 4. 規定に落とす

行き先は `docs/design.md`。

- **値を決め切る。**「明るめの青」ではなく `#2B6CB0`
- **尺度で持つ。**余白は 4 の倍数、字は 4 段、角丸は 2 段。
  **中間値を作らない**(1 つ作ると際限なく増える)
- **状態の扱いも規定に書く。**空・読み込み中・エラー・長文。
  **空が既定の状態**なので、ここを飛ばさない
- **`badge` の `success` / `warning` / `info` のように、意味で名前を付ける。**
  色名で名前を付けない
- **「画面はこの値だけを使う。ベタ書きしない」を 1 行書く**
- 決めた理由を 1 行ずつ添える。**理由の無い規定は、次の人が平気で破る**

skill `single-source` に従う。**CLAUDE.md に写さない。**CLAUDE.md からは
`docs/design.md` を 1 行で指す。

## 5. 当てる

**`globals.css` と `tailwind.config.ts` に置いてから、画面を寄せる。**
逆順にすると散ったまま増える。

1. トークンの定義を作るか直す(**ここが唯一の出どころ**)
2. **変える画面の一覧と、値の対応表 (before → after) を見せて承認を取る**
3. 1 画面ずつ当てる。`--renew` でも**全画面を一度に書き換えない**
4. ベタ書きを消してトークン参照に替える。**消す前にその値が規定にあるか確かめる**
5. `cd frontend && pnpm test && pnpm build` を通す
6. 動かして見る(`bash scripts/dev.sh`)。撮れるなら画面を撮って見せる

**規定に無い値が要ると分かったら、画面に足さず規定へ戻る。**そこで例外を
作ると、規定は 1 か月で飾りになる。

## 6. 確かめる

2 節と同じコマンドを回し直す。

- **値の種類は減ったか。**減っていなければ寄せ切れていない
- 規定に無い値が残っていないか
- **空・エラー・長文の見え方**が変わっていないか
- `docs/images/` の画面キャプチャが古くなっていないか
  (README と portfolio-site の両方が参照している)

## 7. 判断を残す

規定から外すと決めたものは `.claude/judgments.yml` へ(書式は `/code` の 5 節)。
**「この画面だけ例外」は必ず理由と期限つきで書く。**

## 8. 報告

- **選んだ方向と、捨てた案。**なぜ捨てたか 1 行ずつ
- 値の種類 **before → after**(「色 14 種類 → 5 種類」の形で)
- 当てた画面と、**当てなかった画面とその理由**
- 規定に**書かなかったこと**とその理由
- **`docs/design.md` がまた伸びたなら、その行数**
