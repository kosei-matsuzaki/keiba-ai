**機械は候補しか出せない。**1,071 行のファイルを分けるべきか、2 つの関数を
まとめてよいか、そのコメントが「なぜ」か言い換えかは、**読まないと決まらない**。
ここがそれをやり、決めたぶんだけ直す。

## 1. 対象を決める

```bash
K=$(ls ~/.claude/plugins/cache/*/claude-keeper/*/scripts/k.py 2>/dev/null | head -1)
[ -n "$K" ] && python3 "$K" check --only code || echo "claude-keeper 未導入。機械の候補なしで進める"
```

| 引数 | 対象 |
|---|---|
| なし | 未コミットの差分 |
| パス | そのファイル / ディレクトリ |
| `--since <ref>` | その参照からの差分 |
| `--all` | 全体。**10 ファイルを超えるならどこから見るか聞く** |
| `--read-only` | 読んで報告するだけ。直さない |

**読める量に絞る。**全部を薄く見るより、5 ファイルを最後まで読むほうが役に立つ。
機械の出力は**どこから読むかの順番**としてだけ使う。

**先に台帳を読む。**`.claude/judgments.yml` に 49 件の「このままでよい」が
既にある。**蒸し返すなら、何が変わったかを言う。**

## 2. 読ませる

`.claude/agents/code-steward.md` へ投げる(会話の経緯は渡さない)。

**機械が絶対に見つけられないもの**を探す。ここが読む理由:

| 種類 | 例 |
|---|---|
| 名前も形も違うが、同じことをしている | 片方は `for`、片方は内包表記で同じ集計 |
| 同じ概念が別々の形で表れている | 買い目の文字列の正規化が 2 箇所で別々 |
| 同じものを指す別々の名前 | 「確信度」「確率」「hit_prob」が同じもの |
| 1 つの関数に混ざった高さの違う操作 | 「窓を決める」と「小数を丸める」が並ぶ |
| **この構造がこのプロジェクトに合っているか** | 実験の残骸が本番の経路に残っていないか |

### このプロジェクトで特に見るところ

- **`backend/scripts/` は共通化しない。**1 検証 1 ファイルで、写しを
  まとめると過去の実験が再現しなくなる。規約の `code.scope` から外してある。
  見るのは**溜まり**だけ(もう回さない検証)
- **廃止の残骸。**EV・Kelly・`STRATEGY_PRESETS`・`combo_calibrators`・
  `stake_units` は全廃済み。名前が残っていないか `grep` する
- **`api/routers/` は薄いはず。**`app` 層は「下の層を呼ぶだけ」。
  `simulation.py` の同型の 2 組は機械が既に拾っている
- **`hooks -> components` の逸脱 (toast の 5 件) は既知で、あえて残してある。**
  規約にそう書いてある。**毎回蒸し返さない**

## 3. 仕分ける

**直す前に一覧を見せて承認を取る。**3 つに分ける。

| 仕分け | 次にすること |
|---|---|
| **直す** | 4 節の該当する手順へ |
| **このままでよい** | **理由とともに台帳へ**(5 節) |
| **規約がずれている** | `.claude/policy.yml` の `code:` を直す提案を出す |

「このままでよい」と「規約を直す」を必ず含める。
**全部を直すべきと言うのは、読んでいない証拠。**

## 4. 直す

承認されたものだけを、**1 つずつ**。1 つ直すごとにテストを回す
(`cd backend && uv run pytest` / `cd frontend && pnpm test`)。

### 分ける — 伸びたファイル・関数

**行数は理由ではなく合図。**切れ目を探す:

- import の使われ方が上下で違うか
- 説明に「〜して、〜する」が入るか
- 状態を持つ部分と、持たない部分に割れるか

**切れ目が無いなら分けない。**役割が 1 つで長いだけのファイルは、割ると読みにくくなる。

### まとめる — 散った同じもの

判断は 1 問だけ: **「同じ理由で変わるか」。**

- 見た目が同じでも、片方だけ将来ルールが変わる予定なら**まとめない**
- 行き先は**下**(`core` / `db`)。横に置かない
- **引数が 3 つを超えたらまとめ方が間違っている。**戻す

### 置き場所を直す — 崩れた構造

| 種類 | 直しかた |
|---|---|
| 近道の import | import を直す |
| 置き場所が違うだけ | ファイルを動かす(**承認を取ってから** `git mv`) |
| **規約が実態に合っていない** | **規約のほうを直す。ここを怖がらない** |

`ai` が `scraper` を直接呼んだら循環。規約でも CLAUDE.md でも禁じている。

### 消す — 残ったもの

**間違えると動くコードを消す唯一の手順。**根拠を 2 つ取ってから:

```bash
git log --oneline -3 -- <パス>
grep -rn "<ファイル名やシンボル>" backend/src frontend/src backend/tests
```

**`backend/tests/` を必ず含める。**規約の `code.scope` は tests を外しているので、
道具には「テストからだけ使われているもの」が使われていないように見える
(台帳に実例がある)。

- **枠組みが名前で拾うものは消さない**(FastAPI のルータ関数・Lightning の
  フック・Alembic の migration)。規約の `code.dead.entrypoints` に足す
- 一覧を見せて**承認を取ってから**消す

### コメントを直す

skill `code-comments` がそのまま作業指示。順番が大事:

1. **コメントアウトされたコードを先に消す**(git に残っている)
2. コードを読めば分かる説明を消す
3. 失われた「なぜ」を 1 行に圧縮して足す
4. **分からないものには足さない。**推測を書くと、次の人が信じる

**比率では何も分からない。**このリポジトリは判断の根拠(実測値・否定された
仮説・踏んだバグの経緯)をコードの隣に残す方針で、台帳に 7 件そう記録されている。
**厚いから減らす、をしない。**減らすなら「これは言い換えだ」と 1 件ずつ示す。

## 5. 判断を残す

「このままでよい」と決めたものは、**必ず `.claude/judgments.yml` に書く。**

```yaml
judgments:
  - path: backend/src/ai/evaluation/backtest.py
    key: "long_function:evaluate"
    decision: "分けない"
    why: "窓の決め方を変える実験が走っている。落ち着いてから切る"
    at: 453
    date: 2026-09-05
```

**機械が出していないもの**(名前の不一致など)は台帳に書かない。報告に書けば足りる。

## 6. 報告

- 直したもの
- **このままでよいと判断したものと、その理由**(ここが成果物)
- 規約を直す提案があれば、その差分
- **読み切れなかった範囲**(あるなら正直に)
