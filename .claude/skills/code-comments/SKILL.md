# コメントの規約

コメントは**コードに書けなかったことだけ**を書く場所。
コードを読めば分かることを書くと、コードが変わったときに嘘になる。
嘘のコメントは、無いコメントより悪い。

判断はいつも同じ 1 問で済む。**「これはコードから読み取れるか」。**
読み取れるなら消す。読み取れないなら書く。

## 1. 書くもの

| 種類 | 例 |
|---|---|
| **なぜこの手なのか** | `// 2 回問い合わせるのは、1 回だと在庫が二重に減るため` |
| **選ばなかった案とその理由** | `// Set を使わないのは、順序が API の契約に入っているため` |
| **前提・単位・範囲** | `// ミリ秒。サーバは秒で返すので 1000 倍してある` |
| **罠と再現条件** | `// iOS 17 では最初の 1 回だけ空が返る。リトライで回避` |
| **出典** | `// 式は Kingma+2014 の (4)。記号もそれに合わせた` |
| **意図的に変なこと** | `// あえて例外を握りつぶす。ここで落ちると保存済みの結果を失う` |

**わざと変なことをしているとき、コメントは必須。** 次に読む人が「バグだ」と思って
直してしまう。「なぜそうなっているか」が書いていないコードは、いずれ戻される。

## 2. 書かないもの

| 禁止 | なぜ |
|---|---|
| `// ユーザーを取得する` の直後に `getUser()` | 名前の言い換え。名前を直せば済む |
| 引数と戻り値の型の列挙 | 型注釈にある。二重に持つと片方が腐る |
| `// 1. 検証する / 2. 保存する` の実況 | 手順はコードの並びが語っている |
| `// 2026-08-30 田中が修正` | git が持っている |
| `// ここは後で直す` (日付も担当も無い) | 誰も直さない。`TODO.md` に移す |
| 区切り線だけの飾り (`// ======`) | 節が要るならファイルを分けるとき |
| 関数の外に置いた長い設計の説明 | `docs/architecture.md` へ。コードに置くと腐る |

**説明が長くなったら、コメントではなく名前と構造で解く。**
20 行のコメントが要る関数は、たいてい 2 つの関数が入っている。

## 3. 消すもの

- **コメントアウトされたコード。** 例外なく消す。git に残っている。
  「戻すかもしれない」なら、戻す条件をコメント 1 行で書いてコードは消す
- **もうそうなっていない説明。** コードと食い違うコメントは、その場で直すか消す
- **生成物の中のコメント。** 触らない。`scope.exclude` に入れる

## 4. 置き場所

| 位置 | 書くこと |
|---|---|
| ファイルの先頭 | このファイルが何のためにあるか。**1〜3 行**。長いなら docs へ |
| 関数の直前 | 呼ぶ側が知る必要のあること(前提・副作用・失敗のしかた) |
| 関数の中 | その 1 行がなぜ必要か。**直前の 1 行だけ**にかかる形で |
| 型・定数の横 | 単位と範囲 |

言語ごとの形は**そのリポジトリの既存のコードに合わせる**。
python は docstring、TS は公開 API に JSDoc、dart は `///`、go は
`// 関数名 で始める` — 揃っていないものを新しく増やさない。

## 5. 量

- 連続 15 行を超えるコメントは、**docs へ移して 1 行のリンクにする**
- コメント行がコード行の 3 割を超えたら、たいてい言い換えが混じっている
- 逆に、**40 行を超える関数に説明が 1 つも無いのは書き足りない**。
  何のためにあるかを 1 行足す(足せないなら、その関数は何をしているか自分でも
  分かっていない。先に分ける)

## 6. 直すときの手順

1. **コメントアウトされたコードを先に消す。** これだけで量が減る
2. 残ったコメントを 1 つずつ「コードから読み取れるか」で見る。読み取れるものを消す
3. 消した結果、**なぜが失われるところだけ 1 行に圧縮して残す**
4. 説明の無い長い関数に 1 行足す
5. 嘘になっているコメントを直す

**迷ったら消す。** ただし 1 節の表に当たるものは、迷ったら残す。
消したものは git から戻せるが、**失われた「なぜ」は誰も復元できない。**
