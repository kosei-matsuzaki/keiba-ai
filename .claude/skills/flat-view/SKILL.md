# フラットに見る

## なぜ手続きが要るか

同じセッションで書いた Claude は、自分の実装に肩入れする。悪意ではなく、
**会話に残っているものが証拠に混ざる**から:

- 「時間がないので後で直す」と会話で決めた → コードは未完成なのに、完成として読む
- 「この設計にした理由」を会話で説明した → リポジトリに 1 行も書いていないのに、
  書いてある気になる
- 自分が 3 時間かけて書いた → 捨てる案が最初から候補に入らない

**フラットさは態度ではなく手続きで作る。** 「公平に見よう」と思っても効かない。
次の 5 つを機械的にやる。

## 1. 文脈を捨てる

**証拠にしてよいのは、リポジトリに残っているものだけ。** コード、docs、git log、
issue。会話で聞いた話は、どれだけ確かでも根拠に使わない。

これが、役を**サブエージェントに置く理由**。並列に走らせて速くするためではなく、
**会話の記憶を持ち込ませない**ため。自分が書いたコードを自分でレビューするときは、
必ず別の agent に、会話文脈なしで見せる。

会話でしか知らないことに気づいたら、それは所見になる:

> 「なぜ再送を 3 回にしたか」の理由がリポジトリに無い。コードにもコミットにも
> docs にも書かれていない。決めた人が消えたら誰も動かせない。

## 2. 読む順番を変える

docs を検証するときは、**docs を先に読み、実装を見る前に「これが本当なら何が
できるはずか」を書き出す。** そのあと実装で 1 つずつ確かめる。

逆順 (実装を読んでから docs を読む) だと、docs の記述を実装で補って読んでしまい、
**足りない記述と間違った記述が両方とも見えなくなる。**

| 見るもの | 判定 |
|---|---|
| docs にあり、実装にある | 合っている |
| docs にあり、実装に無い | **嘘。いちばん高くつく** |
| docs に無く、実装にある | 抜け。使われていないなら消す候補 |
| docs にあるが、動かすと違う | 古い。動かして確かめる |

**「書いてあるから正しい」を一度も使わない。**

## 3. 意図を聞かない

「なぜこうなっているか」の答えは、コード・コミット・docs のどれかにしか無い。
どこにも無ければ、答えは「理由が残っていない」。それが所見。

作者 (このセッションの Claude や利用者) に聞いて答えをもらうのは、
**証拠を作ることであって、見つけることではない。**

## 4. 賛成を先に書かない

良い点から書くと、そのあとの指摘が全部「ただし」になって弱くなる。
順番は **所見 → 根拠 → 効き方**。良い点は、書くなら最後に 1 行。

**全部を直すべきと言うのも、読んでいない証拠。** 見たものは必ず
「直す / いまは直さない / 判断できない」の 3 つに分ける。3 つ目を隠さない。

## 5. 主張と印象を分ける

所見には必ず場所を付ける。付かないものは印象で、印象は印象として書く。

```
所見: 決済の失敗時に、どこにも記録が残らない
根拠: src/payment/charge.ts:88 の catch が空。ログも再送も無い
効き方: 落ちたことに気づけない。利用者から言われて初めて分かる
確からしさ: 確か (読んだ)

所見: 設定画面が使われていない気がする
根拠: 無い。導線が 2 階層深いのを見ただけ
確からしさ: 推測 (計測していない)
```

## フラットさが壊れているときの兆候

見つけたら止まって、1 節からやり直す。

- 自分がさっき書いたコードを、同じ文脈のまま見ている
- 根拠に「会話で決めた」「時間がない」「後で直す予定」が混ざっている
- docs に書いてあることを、実装で確かめずに前提にした
- 指摘が全部「軽微」で、直す提案が 1 件も無い
- 利用者が一度も出てこない (機能の話をしているのに)
- 数を並べて凄みを出している (「23 件の問題を検出」)。件数は判断ではない

## 書かないこと

- 好みを規約のように言う (「一般にこう書くべき」)。**このリポジトリの証拠で言う**
- 直し方の無い批判。直すか、いまは直さないかを必ず添える
- 前に「いまは直さない」と決めたことの蒸し返し。台帳
  (`.claude/judgments.yml`) を先に読み、覆すなら**何が変わったか**を言う
