#### 推論時に履歴を渡し忘れていた件（2026-08-23 修正）

arch-3 の ability エンコーダは per-race 履歴 GRU を持ち、その系列は **推論時に DB から
leak-safe に組み立てる**（`predict_race(..., session=...)`）。ところが `session` を渡して
いたのは `predict_race_with_combinations` だけで、**素の `predict_race` を呼ぶ経路が全滅**
していた（backtest / simulation engine / `/api/predictions` / `/api/recommendations`）。
`session=None` は履歴 zero に degrade するので、**学習時に評価したモデルとは別物**を
本番で動かしていたことになる。同一レスポンス内で単複確率だけ履歴なし・連系確率は履歴あり、
という不整合も起きていた。

同一レース集合（test 19ヶ月・5,404レース）での paired 比較:

| | 履歴あり（修正後） | 履歴なし（修正前） |
|---|---|---|
| **単勝回収率** | **0.912** | 0.823 |
| 単勝的中率 | 0.213 | 0.204 |
| 賭け点数 | 5,928 | 6,246 |
| top-1 的中率 | 0.2311 | 0.2313 |
| top-1 一致率 | — | 0.385（6割超のレースで 1 番手が別馬） |
| スコアの Spearman | — | 0.835 |

**着順精度（top-1 的中率）はほぼ不変なのに回収率だけ +0.089 動く。** 順位は似ていても
確率の校正が崩れており、賭けなくてよい馬まで EV 閾値を超えていた（点数 6,246 → 5,928）。
ROI を触るときは「順位が合っているか」ではなく「確率が校正されているか」を見ること。

修正後のバックテスト CLI（`--baseline favorite`, EV>1.1, 定額100円）:

| | モデル | 1番人気ベタ買い | 差 |
|---|---|---|---|
| 単勝回収率 | **0.912** | 0.792 | **+0.121** |
| 複勝回収率 | 0.648 | 0.850 | −0.203 |
| top-1 的中率 | 0.231 | 0.332 | −0.101 |

> **複勝ルールは別途要見直し**: 現行の複勝条件（`place_prob × 推定複勝オッズ > 1.05`）は
> 5,404 レースで **43,994 点**（8点/レース）も発火して回収率 0.648 まで落ちている。
> 単勝側（5,928 点 = 1.1点/レース）と比べて明らかに閾値が緩い。モデルではなく戦略の問題。

#### ability-overlay 戦略の検証（2026-08-23・**否定的**）

本節冒頭の「未検証の唯一の道 = ability モデルの予測が odds と乖離する overlay を突く戦略」を
実測した（`scripts/ability_overlay_sweep.py`）。arch-3 は ability エンコーダに odds が入らない
ので、`odds_features=None` で forward すれば **再学習なしで** ability-only スコアが取れる
（標準化済みオッズの平均 = 市場が無意見だった場合の反実仮想）。test 19ヶ月・5,404レース、
温度は valid 窓で **NLL 最小化**（payback グリッド探索だと校正に ROI 追求が混ざるため）。

| 戦略 | 点数 | 的中率 | 単勝回収率 | 95% CI |
|---|---|---|---|---|
| ability EV>1.1（全馬） | 45,876 | 0.017 | 0.697 | [0.63, 0.77] |
| ability EV>1.1（ability 上位3頭） | 9,649 | 0.024 | 0.831 | [0.67, 1.00] |
| ability EV>2.5（ability 1番手のみ） | 2,349 | 0.019 | **0.880** | [0.58, 1.20] |
| overlay比 p/q>1.1（上位3頭） | 10,563 | 0.030 | 0.842 | [0.70, 1.00] |
| **本番ルール（with-odds, EV>1.1）** | 5,928 | 0.213 | **0.912** | — |
| 1番人気ベタ買い | 5,404 | 0.332 | 0.790 | [0.76, 0.82] |

**結論: overlay に edge は無い。** 最良の ability 系（0.880）でも本番（0.912）に届かず、
CI [0.58, 1.20] は 1番人気ベタ買いとも本番とも区別できない幅。決定的なのは温度で、
**ability の NLL 最適温度はグリッド上限 6.0 に張り付き**（本番は 2.8）、NLL も 2.547 対 2.194。
odds を抜くとスコアはほとんど平坦＝情報が無いということで、平坦な確率 × 大穴オッズが
大量の偽 EV を生む（全馬に賭けると 45,876 点・的中率 1.7%・回収率 0.70）。
上位に絞るほど改善するのは overlay の力ではなく、単に平坦確率の罠を切っているだけ。

> 注意: 本スクリプト内の「production_ev」列は NLL 温度で再計算しているため 0.70 になり、
> **本番の 0.912 とは別物**（本番は payback 最適の `temperature_scaler` を使い、点数が
> 44,645 → 5,928 と桁違いに少ない）。比較対象には backtest CLI の実測 0.912 を使うこと。

これで docs が挙げていた 3 つの道（特徴量ノブ / 損失 / 戦略側 overlay）はすべて否定された。
残るのは **市場に無い新情報**（pace / sectional / 馬場差 / オッズ時系列）だけ。

### 実験ノブと A/B 知見（2026-06〜08）

「事前データ処理・特徴量・損失関数で本番 ROI を改善できるか」を検証した一連の
A/B。すべて **env-gated / `--loss` オプションで default-off・inert**（本番アクティブ
モデルに無影響）で実装済み。harness は `scripts/model_side_ab.py`
（`python -m scripts.model_side_ab --knob <name>`、同一 seed で baseline↔treatment を
paired 比較、`persist=False` で models/・keiba.db 非書込）。

| ノブ | 有効化 | 内容 | 実装 |
|---|---|---|---|
| A1 欠損インジケータ | `KEIBA_MISSING_INDICATORS=1` | 新馬/新騎手/血統不明等の欠損源に `*_is_missing` フラグ | `features/builder.py` |
| A2 log 変換 | `KEIBA_LOG_FEATURES=1`（`KEIBA_LOG_FEATURE_COLS` で列上書き） | `odds_win`/`days_since_last_race`/`recent_n_starts` を log1p→標準化 | `ai/model/preprocess.py` |
| B1 タイム指数 | `KEIBA_SPEED_FIGURE=1` | par-time + track-variant 補正済み speed_fig を履歴トークンに追加（17次元）。par は train-fit・`speed_figure.pkl` として永続化 | `features/speed_figure.py` / `features/history_sequence.py` |
| B2 ペース想定 | `KEIBA_PACE_FEATURES=1` | `projected_pace`（先行馬比率）+ `pace_fit`（脚質×ペース交互作用） | `features/extractors/relative_features.py` |
| B3 レース内相対 | `KEIBA_RELATIVE_FORM=1` | 上がり3F・走破時計のレース内偏差と、上がり順位のパーセンタイル（3 列）。生の秒数から「その日の時計水準」を落とす | `features/extractors/horse_history.py` |
| L1 デプロイ整合損失 | `--loss kelly_deploy` | 実ベット決定（EV>0のみ・棄権・edge比例 Kelly）を微分可能化した単勝 log-growth | `ai/model/loss.py::kelly_deploy_loss` |
| L2 デプロイ整合損失（定額） | `--loss flat_ev` | **当時の**賭け方（EV 閾値超えに 1 点定額）を微分可能化。その賭け方は廃止済みで、現在のデプロイとは整合しない。gate=sigmoid((p·o−τ)/T) の期待損益を最大化 | `ai/model/loss.py::flat_ev_loss` |

**結論: 本番（with-odds）の tansho ROI はどれも改善しない**（B3 以外は multi-seed で確認）。

- **A1+A2**: no-odds（ability）は ndcg3 +0.014 とクリーンに改善するが、with-odds は全面悪化（再表現でしかない）。
- **B1（新情報）**: single-seed では有望（no-odds ROI +0.098）に見えたが **multi-seed で霧散**（本番 tansho ROI 平均 −0.03、的中率改善もノイズ）。
- **B2**: 3ノブ中最も明確な負け（本番 全シード・全指標で負、tansho ROI 平均 −0.072）。既存 `recent_early_position_ratio` の派生で新情報がほぼ無い。
- **B3**（2026-08-30）: **log-loss は改善しない。** 判定を回収率ではなく log-loss に置いたのは、
  市場より正確に予測できないモデルが市場より systematically に儲けることは原理的にできず、
  必要条件として回収率より測りやすくノイズに強いため。同一窓・同一 active で確率モデルだけ
  差し替えた paired 比較（2024-11-02〜2026-05-31、5,390 レース）で **off 0.4935 → on 0.4958、
  差 +0.0022 [−0.0016, +0.0062]**。dev・holdout・全窓とも符号は悪化側で揃い、CI は 0 を跨ぐ。
  市場（1/オッズ）の 0.4838 にはどちらも届かない。valid では PL 損失 22.199 → 21.889 /
  ndcg3 0.6103 → 0.6162 と改善するが test では消える（test ndcg3 0.5847 → 0.5841、
  単勝 ROI 0.8237 → 0.8143）。学習は cache 経路・推論は SQL 経路を通るため両方に実装し、
  テストで一致を固定してある。**A/B のときは `KEIBA_DISABLE_FRAME_CACHE=1` を併用する** —
  frame cache のキーは特徴量フラグを含まず、`train_nn` は frame に無い列を黙って落とすので、
  付け忘れるとベースラインのまま完走する（2026-08-30 に 1 本無駄にした）。
- **L1**: 本番 tansho ROI −0.063（全シード負）だが **ndcg3 +0.085 と着順精度は激増**。「精度↑=本命追従（効率価格）=ROI↓」を損失側で最も鮮明に示した。ROI でなく着順精度が欲しい用途では `kelly_deploy` が優秀なランカー。
- **L2**（2026-08-23・`scripts/flat_ev_two_stage_ab.py`）: **単勝 ROI に検出可能な差なし**。seed ごとの
  ばらつき（−0.005〜+0.015）が平均（+0.004）を飲み込んでおり、符号も揃わない。一方
  **ndcg3 は 3 seed とも一貫して悪化**（平均 −0.012）、複勝 ROI・的中率もわずかに負。
  → **「目的関数が Kelly 前提のままなこと」は回収率 <1 の原因ではなかった。**
  なお flat_ev はゼロから学習すると順位を学ばず崩壊する（2 エポックで ndcg3 0.051 /
  log_growth 0.577）。PL 事前学習からの fine-tune が必須。

  | seed | Δ単勝ROI | Δ複勝ROI | Δtop1的中 | ΔNDCG@3 |
  |---|---|---|---|---|
  | 42 | +0.0009 | −0.0038 | ±0.0000 | −0.0160 |
  | 1 | −0.0045 | −0.0023 | −0.0060 | −0.0090 |
  | 7 | +0.0153 | −0.0000 | −0.0081 | −0.0123 |
  | **平均** | **+0.0039** | −0.0021 | −0.0047 | **−0.0124** |

  > 条件: PL 事前学習 10 エポックを両腕で共有し、同一初期値から log_growth / flat_ev を
  > 各 6 エポック fine-tune した **paired 比較**。学習 2024-11-02〜2025-08-31（約10ヶ月）/
  > valid 3ヶ月 / test 2025-12〜2026-05。**本番（10年学習）より大幅に小さい条件**なので、
  > 絶対値の ROI（0.76 前後）は本番の 0.912 と比較できない。測っているのは腕の差だけ。
  > CPU 専用環境（`torch 2.11.0+cpu`）でフレーム構築 ~240 races/min・学習 ~90s/epoch の
  > 制約下で、キャッシュ済み 19ヶ月フレームを流用して 80 分に収めた構成。

いずれも「odds を入力する本番モデルは市場が既に持つ信号を汲み尽くしており、特徴/損失を
変えても予測が odds 最適から離れて ROI が下がる」という市場効率の壁を再確認した。

#### なぜ単勝だけ EV 条件をやめたか（2026-08-24）

温度スケーラが **payback グリッド探索**で T を選んでいた結果 `T_win=0.133` とグリッド下端に
張り付き、`win_prob` が 1 位に **0.999999** 乗っていた（画面に「単勝確率 100.0%」と表示されて
いた）。この状態では `EV = p × odds ≒ odds` なので、`EV > 1.1` は実質「1 位の馬のオッズが
1.1 超か」= ほぼ常に真に退化しており、**表向きの EV ルールと実際の挙動が別物**だった。
`T_place=10.0`（グリッド上端）と併せて、「単勝は 100% と言うのに複勝はほぼ一様」という
互いに矛盾した確率を返していた。

そこで確率は **NLL 較正**（`TemperatureScaler.fit_calibration`、単勝 softmax と複勝 PL で
同じ T を使う）に切り替え、賭け方は確率に依存しないルールとして明示した。test 19ヶ月・
5,404 レースの実測:

| 確率 | 単勝の買い方 | 点数 | 単勝回収率 |
|---|---|---|---|
| 旧（payback 探索 T=0.133） | EV>1.1（実質 1 位買い） | 5,928 | 0.912 |
| **新（NLL 較正 T=2.86）** | **1 位買い + オッズ下限** | **5,376** | **0.931** |
| 新（NLL 較正 T=2.86） | EV>1.1 | 45,001 | 0.698 |

**較正して正直な確率にしたうえで、回収率も +0.019 改善した。** 較正済み確率で EV フィルタを
掛けると、平坦な確率 × 大穴オッズが偽の期待値を量産して 0.698 まで落ちる（overlay 実験と
同じ罠）。較正後の 1 位の単勝確率は **中央値 0.242 / 5-95% 0.122-0.548 / 最大 0.780**。

> **注意: 1 位買いも回収率 1.0 未満**（0.931）。BUY バッジは「+EV だから買う」ではなく
> 「AI の本命はこれ」という意味であり、UI の注記もその通りに書いてある。

#### 複勝も EV 条件をやめた（2026-08-24・**+0.234**）

複勝は EV 条件で 43,464 点（8.1 点/レース）・回収率 0.654 と、1 番人気ベタ買いの複勝 0.850 に

## 戦略レイヤー — どのレースを買うか（2026-08-24 発見 → 2026-08-27 大部分を撤回）

> **⚠️ この節の結論は前進検証で覆った。** 「本命のオッズが 10〜25 倍のレースだけ買えば
> 単勝 1.41」は **period-specific なノイズ**だった。下に経緯を残すのは、
> **dev/holdout で再現しても period-specific な効果は否定できない**という
> 教訓のため。生き残ったのは複勝の確信度フィルタだけ（後述）。

モデルを固定したとき、総合回収率は「レースごとの回収率の、賭け金による加重平均」なので、
動かせるレバーは **(1) どのレースを買うか** と **(2) どのレースに厚く賭けるか** の 2 つ。
どちらも効くのは「**賭ける前に観測できる何か**がそのレースの回収率と相関している場合」だけ。

### 何が起きたか

test 期間 5,390 レース（2024-11-02〜2026-05-31）を前半 dev / 後半 holdout に分けて探索し、
本命のオッズ 10〜25 倍で単勝回収率 **dev 1.42 / holdout 1.41** を得た。信頼区間は 1.0 を
跨がず、半年ごとに割っても全期間で 1.0 超え、メカニズム（同帯の市場勝率 4.60% に対し
モデルの本命は 9.7%）も説明できた。**それでも間違いだった。**

前進検証（`scripts/walk_forward_oof.py`、cutoff を 6 ヶ月ずつ進めて一段目を学習し直し、
毎回まだ見ていない区間だけを予測）で作った **4.5 年・2,092 レース**の out-of-sample
出力で測ると:

| 本命のオッズ | OOF 2020-05〜2024-10 | test 窓 2024-11〜 |
|---|---|---|
| 10〜15 倍 | 0.731 | 1.04 |
| 15〜25 倍 | **0.861** | **1.86** |
| 25 倍以上 | 0.789 | 0.78 |

fold ごとの帯 10〜25: 1.098 / 0.660 / 0.657 / 0.626 / 0.992 / 1.078 / 0.827 / 0.692 / **0.435**。
構造が無い。**最も学習データの多い最後の fold が最悪**なので「一段目が弱いから」でもない。

### なぜ dev/holdout で「再現」したのか

**分割が同じ 19 ヶ月の前半と後半だったから。** ある期間に固有の効果は、その期間を
2 つに割れば当然どちらにも現れる。dev/holdout の分離は「探索したデータで報告しない」
ためには必要だが、**period-specific な効果を否定する力は無い**。それができるのは
「別の期間で測る」ことだけで、前進検証はそのための道具である。

単勝のレース選別は、二段目（一段目の出力を入力に信用度を学習するモデル）を作っても
何も出なかった。**目的変数をシャッフルした対照が上位 10% で最良（1.053）**になる。
単勝には選別可能な信号が無い、というのが現時点の結論。

### 原因: 損失が proper scoring rule ではない

`log_growth` / `multi` は回収率を直接最適化する decision-focused な目的関数で、
**スコアの大きさに確率としての意味を持たせる圧力がかからない**。順序は最適化されるが
magnitude は自由。温度スケーラは全体の鋭さを 1 つの `T` で合わせるだけなので、
レースごとの大小関係の誤りは直せない。EV（`p̂ × オッズ`）が無意味だったのも同じ根で、
`p̂` がノイズなら EV に残るのはオッズだけになる。

## 券種ごとの専用目的と、top-k 打ち切り（2026-08-27〜28）

「1 本のスコアから全券種を PL で導出している」構造への 2 つの手当て。**どちらも
機構としては正しく働いたが、回収率には届かなかった。** 実装は default-off で残す。

### 複勝専用の回収率損失（`--loss place_growth`）

複勝はこれまで自前の目的を持たず、単勝向けに学習したスコアの PL 変換で選んでいた。
レース内では `place_prob` は `score` の単調変換なので、**複勝で買う馬は単勝と必ず
同じ 1 頭**になる。「1 着は苦しいが 3 着内は堅い馬」を選ぶ手段が無い。

実測でも、自前の目的を持つ単勝は市場ベースラインに対し +0.139（0.931 vs 0.792）
なのに、派生の複勝は +0.036（0.886 vs 0.850）しかなかった。

`log_growth` の複勝版を実装した。単勝との違いは**払戻が 3 頭に発生する**ことで、
勝ち馬 1 頭を取り出す形にはならない: `W = 1 + cf·(Σ_i p_i·place_ret_i − 1)`。

**結果（同一 5,353 レースの対比較）**:

| | active | `place_growth` |
|---|---|---|
| 複勝回収率 | 0.8911 | 0.9000（差 +0.009、95%CI [−0.031, +0.048]）|
| dev / holdout | — | **−0.030 / +0.047（符号が反転）** |
| 選ぶ馬が active と一致 | — | 33.9%（2/3 は別の馬）|
| 3 着内率 | 0.5109 | 0.5226 |
| 本命の平均オッズ | 7.74 | 6.09 |

**モデルは狙いどおり「堅い馬」寄りに動いた**（選ぶ馬が変わり、的中率が上がり、
オッズが下がった）。しかし増えた的中が小さくなった配当でちょうど相殺される。
単勝で PL が的中率 0.305 でも回収率 0.824 だったのと同じ構造で、市場は 3 着内確率を
正確に値付けしている。

なお `--place-temp`（softmax の温度を下げて argmax に近づける）も試したが**逆効果**
だった（log-loss 0.5499 → 0.5564、自身の本命の複勝 0.9005 → 0.8750）。
「実運用が argmax だから損失も argmax に寄せる」という理屈は通っていたが、
分布を潰すと学習信号が減る方が勝った。`flat_ev` が効かなかったのと同じ結末。

### PL の top-k 打ち切り（`--pl-top-k`）

`plackett_luce_loss` は全順列を尤度にしていた。しかし払戻が出るのは 3 着までで、
**6 着と 7 着のどちらが上かを当てても 1 円も生まない**。平均出走頭数 14.0 のこの
データでは、上位 3 着だけが重要なら**段の 75.3%** が payout と無関係（上位 5 着
基準でも 58.9%）。先頭 k 段だけを尤度に含めるよう変更した。

**結果（`top_k=5`、同一 5,390 レース）**:

| | 従来（全順列）| top-k=5 |
|---|---|---|
| log-loss | 0.5125 | **0.5080** |
| valid NDCG@3 | 0.5831 | **0.6030** |
| 確信度フィルタの複勝 ROI（holdout）| 0.9453 | 0.9497 |

確率の質と順位精度は改善する。回収率への効果は CI の幅（±0.04）に対して小さく
**検出できない**。ただし**確率モデルの選定は log-loss（proper scoring rule）で行う**
方針なので、この改善を理由に top-k=5 版を採用している。ノイズの大きい ROI で
モデルを選ぶと、オッズ帯で 2 度踏んだ罠に戻るため。

## odds の入れ方を 4 通りに変える（2026-09-02、すべて不採用）

「オッズ 2 列が最後に concat されるのは、出力に影響を与えすぎているのではないか」
という問いから出た一連の A/B。harness は `scripts/model_side_ab.py`、縮小構成
（学習フレーム 2019-01 以降 / batch 128 / 30 epoch / `--base-loss multi`、
test は active と同じ 19 ヶ月）。

### まず現象の確認

ability エンコーダは odds を見ない（`horse_feature_cols` 37 列にも履歴トークン
16 次元にも odds は無い）ので、frame の `odds_win` / `popularity` だけ差し替えれば
head の寄与だけを外せる。active モデル・500 レースで:

| 入力 | 本命的中率 | base と本命が一致 | 順位相関 |
|---|---|---|---|
| そのまま | 0.226 | — | — |
| 全馬同じオッズ（= ability のみ） | 0.090 | 0.422 | 0.446 |
| レース内でシャッフル | 0.100 | 0.318 | 0.235 |

**odds の差を消しただけで本命が 58% のレースで変わる。** 現象としては疑いのとおり。
ただし市場のコピーではない — 本命が 1 番人気と一致するのは 0.408 で、6 割は違う馬。

### 4 通りの介入と結果

| ノブ | 単勝 ROI 差 | ndcg@3 差 | seed |
|---|---|---|---|
| `--odds-dropout 0.3` | **−0.0505**（−0.052 / −0.049） | −0.0140 | 2 |
| `--head-norm joint` | −0.0558（+0.001 / **−0.112**） | −0.0045 | 2 |
| `--odds-route encoder` | **−0.0237**（負 4/4） | −0.0076 | 4 |
| `--head-mode residual` | −0.0093（+0.020 / −0.045 / +0.010 / −0.022） | **−0.0134（負 4/4）** | 4 |

- **dropout**: 学習中だけレース単位で odds をレース平均に潰す。shortcut learning を
  疑ったが、ability が育つどころか順位精度ごと落ちた。**定数倍では検証にならない**
  （concat の直後が Linear なので重みに吸収され、収束後の関数は同一）
- **head-norm joint**: ability だけ LayerNorm し odds 2 列は無加工、という非対称を
  なくす。seed 42 は ±0、seed 1 は −0.112 で、平均は seed 1 一本が作っている
- **odds-route encoder**: odds を馬の特徴として transformer に通す。「head 直結だと
  レース内の相対的な市場位置を作れない」という仮説。**順位精度も上がらなかった**
  （base 0.5316 → 0.5241）。仮説が正しければまず順位が良くなるはずだった
- **head-mode residual**: `score = 市場項(odds) + ability 補正` の加法分解、ability 側は
  0 初期化。ROI は符号がばらけたが ndcg@3 が 4/4 で低下。**ability と odds が隠れ層で
  混ざること自体に価値がある**（モデルは「オッズがこうなら ability をこう読む」という
  交互作用を実際に使っている）

### 測定の限界（ここがいちばんの収穫）

seed 1 の `head-norm joint` は ndcg@3 が base 0.5202 / treat 0.5203 と小数第 4 位まで
同じなのに、単勝 ROI だけ 0.884 → 0.772 に動いた。**差は「上位に来た馬がたまたま
何倍だったか」という裾の運**。さらに `valid_tansho_roi`（モデル選択の基準）と
test ROI がほとんど対応していない。

> この規模で解像できるのは **ROI で 0.05 / ndcg@3 で 0.01** 程度。
> **順位精度を先に見て、ROI は後から見る。**

4 ノブとも default-off で残してある。既定は現行の挙動で、保存済みモデルの読み込みも
変わらない（`meta.json` の `head_norm_mode` / `head_mode` / `odds_route` を見る）。

## LightGBM で「市場に勝てる市場」を探す（2026-09-03、見つからず）

上の 4 実験が全部「odds を弱めると損」で終わったので、問いを変えた。**回収率ではなく
確率だけを測る。** 1.0 を超えるには「市場が間違っているところだけ買う」しかなく、
そのためには自分の確率が市場より正しいと言えなければならないため。
スクリプトは `scripts/gbdt_probability_check.py` / `gbdt_exotic_check.py`。
test は 6,163 レース（2024-11-02〜2026-08-23）。

### 単勝: 市場と互角。odds を外すと大差で負ける

| | field NLL | 対 市場 |
|---|---|---|
| GBDT（odds あり） | 1.9192 | −0.0014 |
| 市場（1/オッズ を正規化） | 1.9206 | — |
| GBDT（odds なし） | 2.1064 | **+0.186** |

odds ありは誤差の範囲で市場と同じ。1 番人気のオッズ帯・頭数のどの切り口でも
差は ±0.004 で、**市場が間違っている一角が見つからない**。odds なしは
**全スライスで負ける**（+0.15〜+0.22、例外なし）。

### 連系: 負ける。しかも複雑になるほど差が開く

当たり組合せの NLL（勝率 → Plackett-Luce）:

| 券種 | GBDT+PL | 市場 | 差 | 控除率 |
|---|---|---|---|---|
| 馬連 | 3.2917 | 3.2689 | +0.023 | 22.5% |
| 馬単 | 3.9587 | 3.9248 | +0.034 | 25.0% |
| 三連複 | 4.3818 | 4.2790 | +0.103 | 25.0% |
| 三連単 | 6.0854 | 5.9563 | +0.129 | 27.5% |

「群衆は組合せの多い市場で下手」という期待の逆だった。**勝率では互角なのに連系で
負けるので、損しているのは PL 変換**。PL は「2 着は勝ち馬を除いた再レース」と
仮定するが実際の着順には脚質・展開の依存がある。着順を 1 つ増やすたびにその歪みが
効くので、馬連 +0.023 → 三連単 +0.129 と積み上がる。連系の確率が要るなら
PL から導かず組合せ単位で直接モデル化すべき（ただし追いついても控除率は超えない）。

### 結論と、GBM の使い道

**壁はモデル族でも構造でもなく情報。** 「odds に引っ張られている」のは症状としては
正しいが、外した先に何も無い。1.0 を超えるには市場が持っていない情報が要る。

一方で GBM には使い道がある:

- **確率の質**: 本命の予測確率と勝敗の相関は GBDT **0.241** / 市場 0.238 に対し、
  現行 active（ROI 志向 NN）は **0.073**。`settings.probability_model_path` の枠を
  差し替える価値は高い
- **回転数**: 学習 45 秒（NN は縮小構成で 40 分）。上の A/B が seed 2 本しか回せず
  ROI ノイズに埋もれた原因がこれ

なお LightGBM は 2026-06-04 の `8ff87dd` で撤去されているが、コミットメッセージは
「コードベースを NN 単一パスに簡潔化する」で、**性能で負けたという記録はどこにも
無い**。直前には GBDT を混ぜて改善したコミット（`def06ef`）もある。
撤去の判断は性能ではなく単純化だった、と読むのが正しい。

## 複勝のバリューベット — 単一 holdout で 1.0 を超え、前進検証で消えた（2026-09-03）

「オッズに強く引っ張られているのでは」という問いから、**回収率ではなく確率**を測る
方針に切り替えた一連の検証。1.0 を超えるには「市場が間違っているところだけ買う」
しかなく、そのためには自分の確率が市場より正しいと言えなければならないため。
スクリプトは `scripts/gbdt_probability_check.py` / `gbdt_exotic_check.py` /
`place_probability_compare.py` / `place_market_edge.py` / `place_edge_walk_forward.py`。

### 見つけたこと 1: 複勝の確率では市場に勝つ

3 着内率の NLL（84,054 頭 / 6,014 レース、2024-11〜2026-08）:

| | NLL |
|---|---|
| **gbdt** | **0.4011** |
| 市場（下限 = 保証される額） | 0.4061 |
| 市場（中点） | 0.4177 |
| 市場（上限） | 0.4420 |
| 現行の確率モデル（NN・別窓 1,200 レース） | 0.4153（同窓の gbdt 0.4083） |

複勝オッズは `[下限, 上限]` の幅を持つ（元返し保証の穴埋めが他の 2 頭の取り分から
出るため、当たった 3 頭の組合せで払戻が変わる）。**両端で測っても勝つ**ので、幅の
扱いで結論はひっくり返らない。単勝では ±0.0014 の互角だったので、複勝市場のほうが
粗いのは確か。

### 見つけたこと 2: EV 選別は効く。ただし 1.0 には届かない

単一 holdout（実払戻・レース単位ブートストラップ）:

| 買う条件 | 点数 | 的中率 | 回収率 | 95% 区間 |
|---|---|---|---|---|
| 全部買う | 84,054 | 0.215 | 0.722 | 0.708–0.737 |
| 本命 1 頭 | 6,014 | 0.654 | 0.862 | 0.845–0.878 |
| EV > 1.00 | 683 | 0.382 | **1.199** | 0.918–1.479 |

**前進検証 12 fold（2019-11〜2025-11、fold ごとに GBDT を学習し直し）で消えた**:

| 規則 | 点数 | 回収率 | 95% 区間 |
|---|---|---|---|
| 閾値を valid で決める | 11,858 | **0.912** | **0.868–0.956** |
| 閾値 1.00 固定 | 3,480 | 0.956 | 0.853–1.064 |

fold ごとは 0.153〜1.739 で、1.0 超えは 12 中 4。決定的なのは **valid で選んだ閾値
のほうが悪い**（0.912 < 0.956）こと。本物のエッジなら valid で最良の閾値は test でも
良いはずで、転移しないということは valid で見えていたのが期間固有のノイズだった、
ということ。オッズ帯の選別（2026-08）とまったく同じ形で、同じように消えた。

> **単一 holdout で 1.0 を超えても信じない。** 3 度目。

ただし **EV 選別の効果自体は大きい**。全部買う 0.722 → EV>1.00 で 0.956 と、控除率
20% のほとんどを取り返している。「勝つ」施策ではないが「損を減らす」施策ではある。

なお CLAUDE.md の「複勝は EV 条件 0.654 で本命買い 0.887 に負ける / EV の順序が逆」は
**壊れた active の確率で測ったもの**。確率を直せば EV は効く（0.722 → 0.956）ことが
実証された。EV そのものが悪いのではなく、入力の確率が悪かった。

### 見つけたこと 3: 連系は PL 変換で損をしている

当たり組合せの NLL（勝率 → Plackett-Luce、6,145 レース）:

| 券種 | GBDT+PL | 市場 | 差 | 控除率 |
|---|---|---|---|---|
| 馬連 | 3.2917 | 3.2689 | +0.023 | 22.5% |
| 馬単 | 3.9587 | 3.9248 | +0.034 | 25.0% |
| 三連複 | 4.3818 | 4.2790 | +0.103 | 25.0% |
| 三連単 | 6.0854 | 5.9563 | +0.129 | 27.5% |

**勝率では市場と互角なのに、そこから作った連系で負ける。** 損しているのは変換のほう。
PL は「2 着は勝ち馬を除いた再レース」と仮定するが、実際の着順には脚質・展開の依存が
ある。着順を 1 つ増やすたびにその歪みが効くので、馬連 +0.023 → 三連単 +0.129 と
積み上がる。連系の確率が要るなら PL から導かず組合せ単位で直接モデル化すべき。

### GBM の位置づけ

LightGBM は 2026-06-04 の `8ff87dd` で撤去されているが、コミットメッセージは
「コードベースを NN 単一パスに簡潔化する」で、**性能で負けたという記録はどこにも
無い**。直前には GBDT を混ぜて改善したコミット（`def06ef`）もある。撤去の判断は
性能ではなく単純化だった。

いま分かっている使い道:

- **確率モデルとして現行 NN より良い**。本命の予測確率と勝敗の相関は GBDT 0.241 /
  市場 0.238 に対し active（ROI 志向 NN）は 0.073。3 着内率の NLL も 0.4083 対 0.4153
- **速い**。1 fold 45 秒（NN は縮小構成で 40 分）。前進検証 12 fold が 5 分で回る。
  odds の A/B が seed 2 本しか回せず ROI ノイズに埋もれたのは、この差が原因

残る穴: EV の計算に**確定オッズ**を使っている。実際に買う時点では確定していない。
`odds.db` に時系列が無いので今のデータでは直せず、この repo の他の回収率
（0.912 等）も同じ前提。前進検証を通っても、この点は残る。

## 計測そのものが壊れていた（2026-09-04、4 件を修正）

回収率の改善を追う前に、**画面に出ていた数字が信用できるか**を見た。4 件とも
「エラーにならず、それらしい値が出る」壊れ方だった。

### 1. 評価窓が学習期間を含んでいた（いちばん重い）

`backtest.py` の `--start` を省くと **DB 全期間**が評価窓になる。確率モデルは
実際にそうなっていて、2015-01-04〜2026-08-23（38,691 レース）で測った
**単勝 0.9447** が画面に出ていた。学習に使った 10 年が窓の大半を占めるので、
これは in-sample の値。未見期間だけで測り直すと **0.8206** になる。

対処は 2 つ:

- `meta.json` の `valid_range` / `train_range` から**モデルが見た最後の日の翌日**を
  既定の開始日にする。窓を省いても in-sample にならない
- `eval_overlaps_train` を metrics に書き、真なら `--persist` を拒否する
  （`--allow-in-sample` で明示的にのみ通す）

### 2. bootstrap が IndexError で落ちる

複勝を確信度で見送った分岐で、複勝側の配列だけ append して**単勝側を append して
いなかった**。レース数が食い違い `index 4832 is out of bounds for axis 0 with size
4561`。長さが揃わなければ例外を投げる guard を足した。

### 3. 交差適合の最初の fold が in-sample で早期停止していた

連系の実験（下記）で、**最初に評価する fold だけ NLL が +0.5〜+1.5 壊れていた**。
early stopping の検証セットを「学習の最後の 1 fold」から取っていたので、学習が
1 fold しかない回では**検証セット = 学習データそのもの**になっていた。
レース単位で後ろ 20% を切る方式に変えて分離した。

> ここで踏んだ一般則: **「検証セットが作れないなら学習データで代用する」は、
> 例外を投げずに静かに間違った数字を出す。** 作れないなら測らない。

### 4. 区間推定が無かった

`--bootstrap-iters` を既定 2000 にして、レース単位のブートストラップで
95% 区間を `metrics_json` に書くようにした。画面にも出す。

### 直した後の active（2024-10-28〜2026-08-23・6,244 レース・本命 1 点）

| 指標 | active | 確率モデル | 市場 |
|---|---|---|---|
| 単勝回収率 | **0.907** [0.844, 0.972] | 0.821 [0.787, 0.856] | — |
| 複勝回収率 | **0.919** [0.892, 0.947] | 0.913 [0.893, 0.936] | — |
| top1 的中率 | 0.230 | 0.308 | — |
| log-loss | 0.570 | 0.608 | **0.482** |

**確率としては市場に負け、回収率では勝っている。** 確率モデルに馬を選ばせると
的中率は上がるが回収率は落ちる（単勝 0.907 → 0.821）という、いままでの結論と整合する。

## 回収率の測定精度 — 「この年数より短い窓の差は読んではいけない」（2026-09-03）

`scripts/roi_measurement_power.py`。test 6,014 レース（1.8 年分）の 1 レースあたり
損益からレース単位ブートストラップで標準誤差を出し、**2 つのモデルの回収率が
0.05 違うと 95% で言うのに必要な期間**を逆算した（1 年 = 3,300 レース）。

| 券種 | 点/R | 回収率 | 標準誤差 | ±0.05 に要る年数 | ±0.03 に要る年数 |
|---|---|---|---|---|---|
| 単勝 | 1.00 | 0.810 | 0.0158 | 5.6 | 15.6 |
| 複勝 | 1.00 | 0.862 | 0.0084 | **1.6** | 4.4 |
| 馬連 | 1.08 | 0.901 | 0.0383 | 8.9 | 24.6 |
| 馬単 | 1.62 | 0.848 | 0.0381 | 9.6 | 26.6 |
| 三連複 | 1.26 | 0.943 | 0.0466 | 15.5 | 43.1 |
| 三連単 | 3.80 | 0.865 | 0.0508 | 19.0 | 52.8 |

**この表がこの半年の失敗をだいたい説明する。** 単一 holdout で見つけた
「効いた」が前進検証で消える件が 3 回あったが、どれも必要期間の 1/3 以下の窓で
出した差だった。複勝だけ 1.6 年と短いのは配当の分散が小さいためで、
複勝の知見（確信度による選別）だけが生き残っているのも同じ理由。

**運用上の帰結**: 連系の A/B は事実上できない。三連単で 0.05 の差を見るのに
19 年かかる。連系については回収率ではなく**確率の質**（NLL）で判断する。

## 連系の確率を PL から作るのをやめ、組合せ単位で直接学習する（2026-09-04〜05）

いまは NN のスコア → Plackett-Luce → 券種ごとの確率、という流れ。PL は
「スコアが強度パラメータ」という仮定を置いており、実際の連系の当たり方と
ずれている可能性がある。**組合せを 1 行にして直接学習したら良くなるか。**

    現行   NN のスコア → PL モンテカルロ → 券種ごとの確率
    直接   NN のスコア → 馬ごとの確率 → 組合せ単位の GBDT → 券種ごとの確率

`scripts/combo_direct_vs_pl_production.py`。**入力を本番と同じ確率モデル**
（`settings.probability_model_path` の NN）にして、PL 確率も特徴量に入れる
（モデルは PL からの「ずれ」だけ学べばよい）。

### 学習量の非対称は構造上避けられない

組合せモデルが使えるのは **NN の未見期間だけ**。NN が学習に使った期間の出力は
過学習した値なので、それに対する補正を学んでも転移しない。よって 2024-10 以降の
22 ヶ月しか使えず、**確率モデル 31,000 レース対 組合せモデル 6,000 レース**になる。

そこで**拡大窓の交差適合**にした。22 ヶ月を時間順に 5 分割し、fold k は 1..k-1 で
学習して k を予測する。全期間を評価に使えるうえ、**学習量を増やしながら測れる**
ので「データ不足なのか、そもそも効かないのか」が分かる。

### 当たり組合せの NLL（小さいほど良い / 6,000 レース）

| 券種 | 学習レース | 直接学習 | 現行 PL | 市場 | 直接 − PL |
|---|---|---|---|---|---|
| 馬連 | 1,200 | 3.4477 | 3.4697 | 3.3464 | −0.022 |
| | 2,400 | 3.3153 | 3.3850 | 3.2319 | −0.070 |
| | 3,600 | 3.3628 | 3.4637 | 3.2978 | **−0.101** |
| | 4,800 | 3.3097 | 3.3918 | 3.2615 | −0.082 |
| 馬単 | 3,600 | 4.0591 | 4.1672 | 3.9678 | −0.108 |
| | 4,800 | 3.9593 | 4.0702 | 3.9094 | **−0.111** |
| ワイド | 3,600 | 2.4731 | 2.5338 | 2.4538 | **−0.061** |
| | 4,800 | 2.4665 | 2.5176 | 2.4596 | −0.051 |
| 三連複 | 1,200 | 4.5423 | 4.4813 | 4.3373 | +0.061 |
| | 3,600 | 4.4013 | 4.4270 | 4.2350 | **−0.026** |
| | 4,800 | 4.4103 | 4.4196 | 4.2719 | −0.009 |

**PL より一貫して良い。** 馬連・馬単で −0.10 前後、ワイドで −0.06。
差は 2,400〜3,600 レースで頭打ちになるので、**22 ヶ月という上限は効いていない**
（データを増やしても伸びない）。三連複は 1,200 レースでは PL に負けており
（+0.061）、3,600 まで増やして初めて追い抜く。組合せ数が多いぶん学習が要る。

一度 1,500 レースだけで測って「三連複は効かない」と早合点したが、
**6,244 レース使えるのに 1,500 しか使っていなかった**のが原因。
学習量を振って測るようにしたのはこの取りこぼしのため。

### まだ入れていない理由

すべての券種で**市場には負けたまま**（馬連 3.31 対 市場 3.26）。PL からの改善は
本物だが、市場との差を埋めるほどではない。加えて**配信に入れる際の運用が重い**:
組合せモデルの学習データは NN の学習打ち切り日に紐づくので、NN を学習し直す
たびに交差適合を K 回やり直す必要がある。効果（NLL −0.1）に対して割に合うかは
未決。回収率で判断できないのは上記の測定精度の表のとおり。
