回収率 100% を超える競馬 AI の作成を目指しているプロジェクトです。netkeiba からのデータ収集、確率推定、買い目提案、収支検証までを自分で作りました。特徴量・損失・モデル族でさまざまなアプローチを検証し、現在はレースを可変長の馬集合として扱う Set Transformer で、単勝 0.907・複勝 0.919 の回収率（out-of-sample・22 ヶ月 6,244 レース）を達成しています。

**見どころ**

- レースを可変長の馬集合として扱う Set Transformer + 履歴 GRU
- 実オッズでの資金成長率を直接最適化する decision-focused loss
- 買う馬を決めるモデルと、確からしさを答えるモデルのアンサンブル

## 回収率で評価できる環境

予想が当たったかどうかと、賭けて増えたかどうかは別物です。機械学習の一般的な指標（精度・AUC）が測るのは前者だけなので、収集から収支検証までを自作し、回収率という 1 つの指標でモデルを選べる環境を用意しました。

### データ

netkeiba から出馬表・レース結果・全馬券種の実オッズを自動収集し SQLite に蓄積

### 推定

各馬の勝率・複勝率に加え、馬連・三連複など連系馬券の的中確率を解析的に導出

### 意思決定

単勝・複勝は AI の本命（予想 1 位）を、連系は的中確率が下限を超えた買い目を、確信度で決まる点数で提示。購入記録と実オッズで収支を検証する

## レースを集合として扱うモデル

出走馬の強さは絶対値ではなく、同じレース内の相対比較で決まります。そこで馬単位の回帰ではなく、レース = 可変長の馬集合を入力とする Set Transformer を採用し、self-attention でレース内の全馬を相互参照させました。各馬の過去走系列は GRU でエンコードして結合しています。

損失は着順の順位学習に加え、実オッズでの log-growth（賭けた場合の資金成長率）を直接最適化します。モデル選択も検証期間の回収率で行うので、選ばれるのは精度の高いモデルではなく、賭けて増えるモデルです。

### 確率は別のモデルに答えさせる

回収率を直接最適化する損失は順序を最適化するだけで、スコアの大きさに確率としての意味を持たせる圧力がかからない（本命の予測確率と実際の勝敗の相関は 0.073・市場は 0.354）。買う馬は回収率で学習したモデルが選び、その馬をどれくらい信じるかは proper scoring rule（Plackett-Luce）で学習した別モデルが答える、と役割を分けた

### リーク防止

特徴量は「レース当日より厳密に過去」の情報だけを SQL の条件レベルで強制する。馬 ID・騎手 ID などの識別子は、暗記を防ぐため特徴量に入れない

### 実験基盤

同一データ分割・複数シードで対照比較する paired A/B ハーネスを整備した。モデルは重み・前処理器・温度スケーラ一式を artifact として保存し、任意の時点で再評価できる

## 確信度で賭け金の厚みを決める

期待値で買う / 買わないを決める方式は全券種で廃止しました。残る問いは「同じ買い方の中で、どのレースに厚く張るか」だけで、判断は確信度（確率モデルがその買い目に付けた的中確率）に一本化しています。

### 券種ごとに最適な判断基準を模索

確信度で 5 分位に切ると、複勝の回収率は 0.749 → 0.911 と単調に上がる。一方の単勝は的中率が 6% → 37% と動くのに回収率は動かない（相関 −0.005）。賭け金を確信度で動かしてよいのは複勝だけ、という非対称を測ってから配分を決めている

### 段階ではなく連続で配分する

倍率を段階で切るのではなく、点数 = 基準 × (確信度 / 0.50)^2 を 1〜15 点に丸める連続配分。前進検証 14,619 レースで複勝回収率は定額 5 点の 0.875 に対し 0.891、しかも 1 レースあたりの点数は 5.42 と段階配分の 8.87 より少ない

## 計測そのものを検証する

回収率を上げにいく前に、画面に出ている数字が信用できるかを確認しました。見つかった 4 件はどれも、例外を出さずにそれらしい値を返す壊れ方でした。

### 評価窓が学習期間を含んでいた

バックテストの開始日を省くと DB の全期間（38,691 レース）が評価窓になり、学習に使った 10 年が大半を占めたままの単勝 0.9447 が画面に出ていた。未見期間だけで測り直すと 0.8206。モデルが見た最後の日の翌日を既定の開始日にし、学習期間と重なる評価は保存そのものを拒否する

### 検証セットが学習データそのものだった

交差適合の early stopping が検証セットを「学習の最後の 1 fold」から取っていたため、学習が 1 fold しかない回では検証セット = 学習データになり、最初の fold だけ NLL が 0.5〜1.5 壊れていた。レース単位で後ろ 20% を切る方式に変更

### 差を読める窓の長さを先に決める

レース単位のブートストラップ 2,000 回で 95% 区間を出し、画面にも表示する。さらに回収率の差 0.05 を 95% で言うのに要る期間を券種ごとに逆算（複勝 1.6 年・単勝 5.6 年・三連単 19 年）。これより短い窓で出した差は読まない、という基準にしている

## 測った値を読むための画面

この道具でいちばん多い操作は買い目を決めることではなく、測った値を読むこと（回収率・的中率・95% 区間・in-sample か OOS か）です。そこで地・罫線・文字は無彩で組み、強い色は枠色 8 色と損益にだけ持たせ、アクセント 1 色は〈測れているか〉だけを指すと決めました。馬が並ぶ画面には枠色が常に 8 色出るので、画面側に色を足すとデータと彩度を奪い合います。箱を積むのはやめて罫線で区切り、数値は等幅＋tabular-nums で桁を揃えています。「今週末のレース」「過去レース」「データ取込」はどれも日付を選ぶ操作なので、カレンダー 1 画面に統合しました。

この規定は `/style` の 1 画面に集約しています。そこに並ぶ数字は実際に描いた要素を `getComputedStyle` で測った値なので、文書と食い違えば実装が変わったとその場で分かります。

新馬戦のように出走馬全員が初出走のレースでは、履歴系の特徴が丸ごと欠けます。出走馬の過去走ゼロ率でレース単位の情報量を測り、レース詳細に「判断材料が少ない」と明示しました。除外しても回収率は動きませんが、買う前に分かること自体に意味があると考えています。

## 節度あるスクレイパー設計

取得先サイトへの負荷を避けることを設計要件として最初に置きました。直列リクエストのみ・最低 3 秒＋ジッター（深夜はさらに延長）・robots.txt 遵守（取得失敗時は fail-closed で全停止）・連絡先を明示した研究用 User-Agent。UI / API / 環境変数の 3 経路から即時停止でき、中断してもレコード単位で再開できます。

## 現在の到達点と、次に入れる情報

確定実オッズ・22 ヶ月 6,244 レースの out-of-sample 検証で、アプリと同じ賭け方をした場合の回収率は単勝 0.907（95% 区間 0.844〜0.972）・複勝 0.919（0.892〜0.947）です。一律購入のベースライン（控除率のため約 0.75〜0.80）も、1 番人気ベタ買い（0.792 / 0.850）も上回っていますが、黒字ライン 1.0 にはまだ届いていません。

検証したアプローチは、特徴量の追加、損失の設計、オッズの入れ方を変える 4 通りの介入、モデル族を LightGBM に替える比較までです。すべて multi-seed A/B で判定し、確率の質だけを測ると LightGBM は単勝の NLL で市場と並びます（1.9192 対 1.9206）が、連系では控除率の大きい券種ほど市場に負けます。4.5 年の前進検証を通ったのは賭け方の側（複勝を確信度で厚くする配分で 0.875 → 0.891）でした。壁はモデル族でも構造でもなく情報の側にあり、公開情報から残るエッジは控除率を覆すには足りない — この市場効率を再現可能な形で確認できています。次は公開オッズに織り込まれていない情報（ペース・区間タイム・馬場差・オッズの時系列）を入れます。

## データソースと権利について

- **個人研究限定**: 取得データ・学習済みモデルは第三者へ提供・公開しません。本リポジトリに含まれるのはソースコードとドキュメントのみです
- **サイト負荷への配慮**: リクエストは直列のみ・最低 3 秒 + ジッター（深夜帯はさらに長く）のレート制御を徹底し、robots.txt を遵守します（取得失敗時は fail-closed = 全リクエスト拒否）。User-Agent は連絡先付きの研究用ボットとして自己申告します
- **即時停止スイッチ**: Race 画面の取込パネル（`DayIngestPanel`）、`/api/scraper/stop` エンドポイント、環境変数 `KEIBA_SCRAPER_STOP=1` の 3 経路で任意のタイミングでスクレイピングを停止できます
- テストフィクスチャはすべて合成 HTML であり、実ページの capture は含まれません
