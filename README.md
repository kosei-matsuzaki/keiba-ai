**見どころ**

- レースを「可変長の馬集合」として扱う Set Transformer + 履歴 GRU
- 実オッズでの資金成長率を直接最適化する decision-focused loss
- 回収率を動かしたのはモデル改良ではなく「評価と本番のズレ」の発見だった

## 課題設定

公営競技の予想は「当たるか」ではなく「賭けて増えるか」で評価されるべきなのに、機械学習の教科書的な指標（精度・AUC）とは目的がずれています。そこで、データ収集から賭け戦略・収支検証までを全部自分で作り、回収率という単一の指標でモデルを評価できる環境を用意しました。

### データ

netkeiba から出馬表・レース結果・全馬券種の実オッズを自動収集し SQLite に蓄積

### 推定

各馬の勝率・複勝率に加え、馬連・三連複など連系馬券の的中確率を解析的に導出

### 意思決定

単勝・複勝は AI の本命（予想 1 位）、連系は期待値が基準を超えた買い目を、1 点定額で予算まで提示し、購入記録と実オッズで収支を検証

## レースを「集合」として扱うモデル

出走馬の強さは絶対値ではなく同じレース内の相対比較で決まります。そのため馬単位の回帰ではなく、レース = 可変長の馬集合を入力とする Set Transformer を採用し、self-attention でレース内の全馬を相互参照させました。各馬の過去走系列は GRU でエンコードして結合しています。

さらにネットワーク内部で「能力の推定」と「オッズ（市場の集合知）の利用」を分離し、市場情報にどれだけ依存させるかを制御できる構成にしました。

## 回収率を直接最適化する損失設計

着順の順位学習（Plackett-Luce）だけでなく、実オッズでの log-growth（賭けた場合の資金成長率）を損失として直接最適化しました。連系馬券確率の NLL を加えた複合損失により、外部の確率校正器を不要にしています。

モデル選択も検証期間の回収率で行い、「精度が高いモデル」ではなく「賭けて増えるモデル」を選ぶ設計です。最良構成は順位損失での事前学習 → 複合損失への fine-tune の二段階学習でした。

## 確率の一貫性とリーク防止

### 確率導出

単勝は温度スケーリング付き softmax、複勝・連系は Plackett-Luce の解析解 / モンテカルロ。温度は勝ち馬の NLL で較正し、単勝 softmax と複勝 PL で同じ値を使います。全馬券種が単一のスコアベクトルから導かれるため、馬券種間で矛盾した予測が起きません。

### リーク防止

特徴量は「レース当日より厳密に過去」の情報のみを SQL の条件レベルで強制。馬 ID・騎手 ID などの識別子は暗記を防ぐため特徴量に入れません。

### 評価

学習・検証・テストを時系列で分割し、評価は常に out-of-sample。予測時点で未確定のオッズを除外して検証できるスイッチも用意しました。

### 実験基盤

同一データ分割・複数シードで対照比較する paired A/B ハーネスを整備し、モデルは重み・前処理器・温度スケーラ・メタデータ一式を artifact として保存して任意時点で再評価可能にしています。

## 評価と本番がずれていた

回収率を実際に動かしたのは、モデルの改良ではなく「学習時に評価したものと、本番で動いているものが違う」という 3 件のズレの発見でした。いずれも着順の精度はほとんど変わらないのに回収率だけが動きます。

### 推論時に履歴を渡していなかった

能力エンコーダは過去走系列を GRU で読みますが、その系列を組み立てて渡していたのは連系馬券の経路だけで、単複の予測・バックテスト・API はすべて履歴ゼロで動いていました。同一レース集合での paired 比較で単勝回収率 0.823 → 0.912。top-1 的中率は 0.2313 → 0.2311 とほぼ不変で、崩れていたのは順位ではなく確率の校正でした

### 温度スケーラが回収率を見て校正していた

温度を払戻グリッド探索で選んでいたため下限に張り付き、1 位の単勝確率が 0.999999（画面表示 100.0%）になっていました。この状態では期待値フィルタが「オッズが閾値超えか」に退化しており、表向きのルールと実挙動が別物です。NLL 最小化での較正に切り替え、買い方も「モデル 1 位 + オッズ下限」と明示した結果、単勝回収率 0.931（1 番人気ベタ買い 0.792）

### 期待値フィルタの向きが逆だった

同じ問いを複勝でも見ました。確率を正直に較正したうえで期待値で絞ると、1 レースあたり 8.1 点も買って回収率は 0.654 のまま。EV 帯別に実現回収率を並べると「買わない帯」（EV 0.0〜0.9）が 0.832 で最良、EV 2.0 以上が 0.573 で最悪という単調減少で、シグナルの向きが逆でした。温度や Harville 補正の冪のような単調変換は逆向きのものを逆向きのまま再スケールするだけなので原理的に直せません（3 着内 log-loss を最小化した温度は、log-loss は改善しても回収率をむしろ下げました）。期待値フィルタを捨てて単複とも「モデルの本命を買う」に変えた結果、複勝回収率 0.654 → 0.887（1 番人気ベタ買い 0.850）

### そこから決めたこと

評価器がアプリの実行できない戦略を測れる状態そのものがバグの温床です。賭け金の決定は 1 点定額に統一し、評価器に残っていた Kelly も撤去しました（損失関数の内部にある係数は Kelly ではなくオッズを勾配に残すための項なので、名前を改めて残しています）。ダッシュボードの 4 指標も「同じ 1 回の評価」から取るよう揃えました

## 画面を「読み物」ではなく「端末」にする

確率と金額を横断で読む道具なので、余白の広い読み物的な UI から、暗所で数字と枠色が立つオッズ端末寄りの画面に作り替えました。箱を積むのをやめて罫線で区切り、角丸を 2px まで落とし、数値はすべて等幅＋tabular-nums で桁を揃えています。

画面の数も減らしました。「今週末のレース」「過去レース」「データ取込」の 3 つは、結局どれも「日付を選んでその日のレースを見る」ことをしていたので、カレンダー 1 画面に統合して取り込みもそこから行います。

### 買い方をそのまま操作対象に

資金の何 % ではなく「このレースにいくら使うか」「1 点いくらか」「どの券種を買うか」「本命中心か穴も拾うか」を画面に出しました。利用者が実際に考える単位に合わせ、内部の top_n_horses などは表に出しません

### レース後の答え合わせ

推奨した馬が何頭 1 着になり、その予想の回収率がいくらだったかをレース詳細に出します。着順の当たり外れではなく回収率で振り返らせる、というモデル側の設計と画面を一致させました

## 節度あるスクレイパー設計

取得先サイトへの負荷を避けることを設計要件として最初に置きました。直列リクエストのみ・最低 3 秒＋ジッター（深夜はさらに延長）・robots.txt 遵守（取得失敗時は fail-closed で全停止）・連絡先を明示した研究用 User-Agent。UI / API / 環境変数の 3 経路から即時停止でき、中断してもレコード単位で再開できる resume 機構を全ジョブに実装しています。

## 結果と、いちばん重要な学び

確定実オッズ・19 ヶ月 5,404 レースの out-of-sample 検証で、アプリと同じ賭け方をした場合の回収率は単勝 0.931・複勝 0.887。一律購入のベースライン（控除率 20〜25% のため約 0.75〜0.80）も、1 番人気ベタ買い（単勝 0.792 / 複勝 0.850）も上回りましたが、どちらも黒字ライン 1.0 には届きません。診断で見つけた歪みそのもの（推定複勝オッズが穴側で 1.37 倍甘い Harville バイアスと、複勝確率の低確率帯での 2.7 倍の過大評価）は残っていて、買い方を変えることで踏まないようにしただけです。

そのうえで、特徴量追加（欠損フラグ・log 変換・タイム指数・ペース適性）、損失設計（実際の賭け方を微分可能にしたもの）、オッズを入力しないモデルで市場の過小評価を突く戦略まで、multi-seed A/B で検証したものは本番の回収率をひとつも改善しませんでした。オッズが既に持つ情報量が支配的で、公開情報からの残余のエッジは控除率を覆すには足りない — この市場効率を、自前の実験基盤で再現可能な形で確認できたことがこのプロジェクトの到達点だと考えています。ネガティブリザルトを含む全実験の記録をドキュメントに残しています。

## ここからどこへ向かうか

### 予測の説明性

どの特徴が効いたのかを提示する仕組みを再導入する。回収率が伸びない以上、次に価値があるのは「なぜその馬なのか」が読めることだと考えている

### 市場に無い情報

特徴量・損失・戦略の 3 方向が尽きた以上、残るのは公開オッズに織り込まれていない情報（ペース・区間タイム・馬場差・オッズの時系列）を入れること。地方競馬・海外レースへの拡張でデータ量そのものを増やす道も併せて検討している

### 連系の期待値ルール

単複は期待値フィルタを外して本命買いにしたが、連系（馬連・三連複など）は今も推定オッズ × 確率の期待値で買っている。複勝で見つかった「推定オッズが穴側で甘い」「高 EV 帯ほど回収率が低い」が連系でも起きていないかを、同じ診断で確かめる

### 目的の再設定

「儲ける」から「市場の歪みを検出する」へ。期待値の高い歪みがどういう条件で発生するのかを調べる方向に切り替える

## データソースと権利について

- **個人研究限定**: 取得データ・学習済みモデルは第三者へ提供・公開しません。本リポジトリに含まれるのはソースコードとドキュメントのみです
- **サイト負荷への配慮**: リクエストは直列のみ・最低 3 秒 + ジッター（深夜帯はさらに長く）のレート制御を徹底し、robots.txt を遵守します（取得失敗時は fail-closed = 全リクエスト拒否）。User-Agent は連絡先付きの研究用ボットとして自己申告します
- **即時停止スイッチ**: Settings 画面の停止スイッチ、`/api/scraper/stop` エンドポイント、環境変数 `KEIBA_SCRAPER_STOP=1` の 3 経路で任意のタイミングでスクレイピングを停止できます
- テストフィクスチャはすべて合成 HTML であり、実ページの capture は含まれません
